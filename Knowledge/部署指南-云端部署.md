# FoodTime 食光 — 云端部署操作清单

> 目标：把项目部署到公网，得到一个可分享的演示链接。
> 架构：**Vercel（前端静态站） + Railway（后端 + MySQL）**
> 说明：Vercel 无法托管 MySQL，也无法长期运行 FastAPI 进程，因此后端放在 Railway。

---

| 需要的东西 | 说明 |
|---|---|

## 一、部署后端 + 数据库（Railway）

### 1.1 创建项目与 MySQL

1. 登录 [railway.app](https://railway.app) → **New Project**
2. 选择 **Provision MySQL**，等待实例就绪
3. **后端无需手动填数据库变量**：项目已在 `backend/config.py` 里自动映射 Railway 注入的变量
   （`MYSQLHOST` / `MYSQLPORT` / `MYSQLUSER` / `MYSQLPASSWORD` / `MYSQLDATABASE`
   → `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASSWORD` / `DB_NAME`）。

   > 映射规则：**仅当 `DB_HOST` 仍是默认值 `localhost` 时才采用 `MYSQLHOST`**。
   > 因此本地开发（已显式配置 `DB_HOST`）不受影响，而 Railway 上后端会
   > **自动走内网** `mysql.railway.internal:3306` —— 不走公网代理，更快且不暴露端口。

   如需覆盖，照常设置 `DB_HOST` 等变量即可（显式配置优先）。

   | Railway 变量 | 映射为 | 说明 |
   |---|---|---|
   | `MYSQLHOST` | `DB_HOST` | 内网域名 `mysql.railway.internal` |
   | `MYSQLPORT` | `DB_PORT` | 内网端口 `3306` |
   | `MYSQLUSER` | `DB_USER` | 默认 `root` |
   | `MYSQLPASSWORD` | `DB_PASSWORD` | 自动读取 |
   | `MYSQLDATABASE` | `DB_NAME` | 通常是 `railway` |

> ⚠️ **内网域名 `mysql.railway.internal` 只能被 Railway 容器内部访问**，
> 本机解析会报 `getaddrinfo failed`。因此下面的「导入表结构」步骤若在本机执行，
> **必须**先在 MySQL 服务 → `Settings` → `Networking` → **TCP Proxy** 开启公网代理，
> 拿到 `xxx.proxy.rlwy.net:PORT` 形式的地址后才能连上。

### 1.2 导入表结构与种子数据

数据库是空的，必须手动导入。项目提供了专用脚本：

> **执行位置**：本机（需公网代理地址，见上方 ⚠️）。
> 已实测 `root@%` 可直接从公网连接，无需另建用户；PyMySQL 连接需带 SSL。

```bash
# 在项目根目录执行
cd C:\Users\zjy\Desktop\校招\FoodTime

# 方式 A：直接用连接串（从 Railway Connect 复制，注意去掉 ? 后面的参数）
backend\venv\Scripts\python.exe sql\deploy_init_db.py "mysql://root:PASSWORD@HOST:PORT/railway"

# 方式 B：分参数传入
backend\venv\Scripts\python.exe sql\deploy_init_db.py ^
  --host HOST --port PORT --user root --password PASSWORD --db railway
```

> 🚨 **不要把脚本输出接管道**（如 `| tail`）。管道会因 SIGTERM 提前截断进程，
> 但**已写入的数据不会回滚**，重跑时就会产生大量 `1062 Duplicate entry`，
> 看着像「49 成功 3 失败」的失败，实际数据是完整的。
> 正确做法：`... > run.log 2>&1; echo EXIT=$?` 再读日志。

**预期输出**：

```
📐 建表（来源: backend/models.py，共 12 张表）
...
[1/4] 建表          → ✅ 12 张表创建完成
[2/4] 补齐默认值    → ✅ 补齐 123 个默认值
[3/4] 创建视图      → ✅ 3 个视图
[4/4] 导入种子数据  → （无输出即全部成功）
==============================================================
✅ 初始化完成：52 条语句执行成功，0 失败
==============================================================
```

**验证**（预期：12 张表 + 3 个视图，约 103 行数据，`users` 3 行）：

| 表 | 行数 | 表 | 行数 |
|---|---|---|---|
| users | 3 | recipe_cache | 3 |
| user_preferences | 3 | shopping_items | 10 |
| preference_weights | 27 | chat_sessions | 1 |
| cook_records | 16 | chat_turns | 10 |
| takeout_records | 10 | quota_usage | 0 |
| daily_fortunes | 4 | ingredients | 16 |

> 📌 **重要说明（脚本的设计原理）**
>
> 1. **建表以 `backend/models.py` 为唯一真相源**，用 SQLAlchemy 生成 CREATE TABLE。
>    `sql/06_schema_v2_final.sql` 是**过时的老 schema**（它的 users 表只有 9 个字段，
>    缺 `username`/`phone`/`password_hash`/`status`/`token_valid_since`），
>    本地库是靠 `auto_migrate_mysql.py` 事后 ALTER 补齐的，而那个脚本硬编码了
>    本地库名与密码，云端无法使用。**这就是本脚本不直接跑 06 脚本的原因。**
> 2. **自动补齐数据库层默认值**：`models.py` 里的 `default=_uuid` / `default=_now`
>    是 Python 层默认值，SQLAlchemy 不会生成 DDL `DEFAULT`。脚本会检测所有
>    `NOT NULL` 且无默认值的列并补上，否则裸 SQL 插入（种子数据）会报 `1364`。
> 3. **视图**从 06 脚本提取并改为 `CREATE OR REPLACE VIEW`，保证可重复执行。
> 4. 脚本会自动剥离原始的 `CREATE DATABASE makweichuzuwu` / `USE meiweichuzuwu`，
>    因此可安全导入到任意库名的云数据库。
>
> 导入后应有 **12 张表 + 3 个视图**。`updated_at` 由
> `ON UPDATE CURRENT_TIMESTAMP` 自动维护，无需触发器。

### 1.3 部署后端服务

> 🚨 **前提条件（务必先读）**：后端服务必须和 MySQL **建在同一个 Railway 项目内**。
> 本项目已在 `backend/config.py` 自动映射 Railway 注入的 `MYSQL*` 变量，
> **但这依赖 Railway 的同项目变量注入机制** —— 跨项目时 `MYSQLHOST` 不会被注入，
> 后端会退回 `localhost` 并报 `Can't connect to MySQL server on 'localhost'`，
> 表现为接口 502。
>
> **判定方法**：后端服务 → `Variables` 里若能看到灰色的 `MYSQLHOST`/`MYSQLPORT`
> 等（Railway 自动注入，不可编辑），说明同项目、映射生效；
> 看不到则说明跨项目，需按下文手动配置 DB_* 变量。
>
> **启动日志自检**：正常应打印
> `[ENV] 当前运行环境: PRODUCTION (数据库: railway @ mysql.railway.internal:3306) [来源: railway-env(...)]`。
> 若显示 `[来源: default(localhost)]` 且带 `⚠️ 数据库指向 localhost` 提示，
> 即为变量未注入。

1. 在**已经有 MySQL 的那个项目**里 → **New** → **GitHub Repo** → 选 `FoodTime`

   > ⚠️ 不要在 MySQL 项目之外单独新建项目，否则需手动配全部 `DB_*` 变量。

2. 进入该服务 → **Settings**：
   - **Root Directory** 填 `backend` → 回车保存
   - **Build** 选 Dockerfile（会自动识别 `backend/Dockerfile`）

   > ⚠️ 改完 Root Directory 后**必须触发一次 Redeploy** 才生效。

3. 进入 **Variables**，添加以下环境变量：

```ini
# ---- 数据库 ----
# 无需填写任何 DB_*：只要 MySQL 插件【在同一项目内】，后端会自动读取
# Railway 注入的 MYSQLHOST/MYSQLPORT/MYSQLUSER/MYSQLPASSWORD/MYSQLDATABASE
# 并走内网 mysql.railway.internal。若需覆盖再显式设置。
#
# 【跨项目备选】若 Variables 中看不到注入的 MYSQL*，则手动补：
# DB_HOST=<MYSQLHOST 或公网代理主机>
# DB_PORT=<MYSQLPORT 或公网代理端口>
# DB_USER=root
# DB_PASSWORD=<MYSQLPASSWORD>
# DB_NAME=railway
DB_TYPE=mysql

# ---- 运行环境 ----
APP_ENV=production
DEBUG=false
SECRET_KEY=<自己生成一串 64 位随机十六进制>
CORS_ORIGINS=https://*.vercel.app

# ---- LLM（按需填写，留空则走 mock 兜底）----
DEEPSEEK_API_KEY=<你的 key>
DASHSCOPE_API_KEY=<你的 key>

# ---- 连接池（云库连接数有限，保持默认即可）----
DB_POOL_SIZE=5
DB_MAX_OVERFLOW=5
```

4. **生成公网域名**：服务 → `Settings` → `Networking` → `Public Networking`
   → `Generate Domain`

   > 端口填 **`8000`**。容器内实际监听 `${PORT:-8000}`，Railway 注入 `PORT` 后
   > 常见为 `8080`，Dockerfile 已自适应，无需手动改。

5. **验收**：

```bash
# 应返回 {"code":0,...,"data":{"status":"ok",...}}
curl https://<你的域名>/api/health

# /docs 应返回 404（production 已关闭），属正常
```

> 🔒 内网连接不需要公网代理，也**不需要把数据库密码写进后端变量** —— 更安全。
> 公网代理只在第 1.2 步「本机导入表结构」时需要临时开启，导入完可以关掉。

> 🔑 **SECRET_KEY 生成方法**（任选一种）：
> ```bash
> python -c "import secrets; print(secrets.token_hex(32))"
> ```
> 不要使用仓库里的占位值，否则重启后所有登录态失效。

4. **Settings → Networking → Generate Domain**，拿到后端公网地址，形如：
   `https://foodtime-backend-production.up.railway.app`

5. 验证后端：
   ```bash
   curl https://你的后端域名.up.railway.app/api/health
   # 期望：{"code":0,"message":"ok","data":{"status":"ok",...}}
   ```

## 二、部署前端（Vercel）

### 2.1 导入项目

1. 登录 [vercel.com](https://vercel.com) → **Add New → Project**
2. 选择 `FoodTime` 仓库
3. **Root Directory** 设置为 `frontend`（重要！）
4. Framework Preset 会自动识别为 **Vite**（`vercel.json` 已配好构建命令与 SPA 重写）

### 2.2 配置环境变量

在 **Environment Variables** 添加：

| Name | Value |
|---|---|
| `VITE_API_BASE` | `https://你的后端域名.up.railway.app/api` |

> ⚠️ 必须是 **`/api` 结尾**，且**不能有末尾斜杠**。
> `VITE_*` 变量会被编译进前端产物，**不要放任何密钥**。

5. 点 **Deploy**，等待构建完成，拿到前端地址，形如：
   `https://foodtime-xxxx.vercel.app`

### 2.3 验证跨域

后端已支持 `https://*.vercel.app` 通配符，因此**预览域名也能直接访问**，无需逐个添加。
若浏览器控制台出现 CORS 报错，检查 Railway 的 `CORS_ORIGINS` 是否为 `https://*.vercel.app`。

## 四、常见问题

### Q1: 前端报 `Failed to fetch` / Network Error
- 检查 `VITE_API_BASE` 是否漏了 `/api` 后缀
- 检查后端域名是否可访问（直接 curl `/api/health`）
- 检查 Railway 服务是否处于 Running 状态

### Q2: 后端部署后立刻崩溃退出
- 查看 Railway **Deploy Logs**
- 最常见原因：`DB_*` 变量填错导致连不上数据库
- 其次：`SECRET_KEY` 未配置（不会崩，但会警告）

### Q3: 注册 / 登录返回 500（错误码 5001 数据库服务异常）
- **典型日志**：`Unknown column 'users.username' in 'field list'`
- **原因**：数据库初始化时用了过时的 `sql/06_schema_v2_final.sql` 建表
- **解决**：重新执行 `sql/deploy_init_db.py`（新版已改为从 `models.py` 生成表结构）
- **自检命令**：
  ```bash
  # 应输出 username, phone, password_hash, status, token_valid_since
  mysql -h HOST -u root -p -e "SHOW COLUMNS FROM users;" railway
  ```

### Q4: 种子数据导入报 1364（Field 'xxx' doesn't have a default value）
- **原因**：`models.py` 的 Python 层默认值未落到数据库
- **解决**：新版 `deploy_init_db.py` 已自动补齐（会打印「补齐 N 个默认值」）
- 若仍有少量列被跳过，脚本会列出清单，手动 `ALTER TABLE ... MODIFY COLUMN ... DEFAULT ...` 即可

### Q5: Railway 日志显示数据库连接数超限
- 把 `DB_POOL_SIZE` 和 `DB_MAX_OVERFLOW` 调小（如 `2` 和 `2`）
- 免费层 MySQL 连接数上限较低

### Q6: AI 功能返回的是固定内容，不像真 AI
- 检查 `DEEPSEEK_API_KEY` / `DASHSCOPE_API_KEY` 是否配置正确
- 未配置时会走 `llm_service` 的 mock 兜底（不报错，但内容是预设的）

### Q7: 想换绑自己的域名
- Vercel：Project → Settings → Domains → 添加
- 添加后记得把新域名加进 Railway 的 `CORS_ORIGINS`（逗号分隔，可混用通配符）

### Q8: 重新导入数据库时报「表已存在」
- `06_schema_v2_final.sql` 开头有 `DROP TABLE IF EXISTS`，重跑即可
- 或者先手动 `DROP DATABASE` 再重建

## 五、成本与安全提示

| 项目 | 说明 |
|---|---|
| Vercel | 免费层：100GB 带宽/月，个人演示足够 |

## 六、本地开发不受影响

本次改动均为**向后兼容**，本地启动方式不变（见 `Start.txt`）：

```bash
# 后端
cd backend && python -m uvicorn main:app --host 127.0.0.1 --port 8000 --reload

# 前端
cd frontend && npm run dev
```

本地未设置 `VITE_API_BASE` 时，前端自动回退到 `/api` 相对路径，继续走 Vite 代理。
